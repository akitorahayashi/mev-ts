# レビュー返信コメント

レビュー指摘と差分を読み、修正の主要な因果関係をコード上で追える返信コメントとして出力する。

## 入力

- ファイル、コミット、差分が指定されていれば、それを対象とする。
- 指定がなければ未コミット差分を調べる。作業ツリーがクリーンなら、upstreamより先行しているコミットを調べる。
- レビュー指摘の意図が差分だけでは分からない場合は、呼び出し元まで調査する。それでも判断できない場合だけユーザーへ確認する。

## 出力の目的

読み手が一読して、次の2点をコードで確認できる状態にする。

- 何が指摘された問題の原因だったか
- どの処理をどう変えて解決したか

差分の全変更を要約することは目的ではない。報告対象は、指摘された問題を解決した主要な変更である。

## 返信の組み立て

既定は2文とする。

1. 原因: 所有するクラスやメソッドを示し、何が何より先に動いたか、どの条件や値が誤っていたかを書く。
2. 修正: 原因と同じ粒度で、順序、条件、または値をどう変えたかを書く。

原因が実行順なら修正も実行順で説明する。原因が判定条件なら修正も判定条件で説明する。原因と修正の説明を別の粒度にしない。

クラス名やメソッド名はコードを追う手掛かりとして使う。補助変数、ガード、取得方法などは、それ自体が指摘対象か、解決の成立に不可欠な場合だけ含める。

誤認や調査の経緯は、レビューで理由を問われている場合だけ書く。通常は、修正前のコード上の原因を述べる。

## 文体と形式

- そのまま投稿できる返信文だけを出力する。
- 短い修正は平文1〜2文にする。
- ファイルパス、行番号、コードブロックは含めない。
- 副作用への言及は、指摘との関係があり、呼び出し元から根拠を示せる場合だけ加える。
- 複数の指摘には、指摘ごとに対応が分かる返信を作る。同じ修正で対応した場合も各スレッド向けに分ける。

## 最終確認

出力前に次を確認する。

- 原因と修正が直接つながっているか。
- 読み手がクラス名またはメソッド名から変更箇所を追えるか。
- 差分の補助的な変更を、主要な解決策のように説明していないか。
- 各文を削ったときに必要な情報が失われるか。失われない文は削る。
