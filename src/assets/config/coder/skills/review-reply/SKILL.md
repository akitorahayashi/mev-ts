# レビュー返信コメント

差分を読み、レビュー指摘に対する修正の内容と理由を上司が読める返信コメントとして出力する。

## 入力

ユーザーから特定のファイルやコミットの指定がない限り、現在の作業ツリーにおける未コミットの変更（`git diff`等）を自ら調べて対象とする。明示的に差分テキストが与えられた場合はそれを使用する。

## 出力の目的

修正の意図を上司に伝えること。上司はコードを読むが、変更の背景や判断の理由は差分だけではわからない。返信コメントがその橋渡しをする。

## 出力フォーマット

Markdown。構造は内容に応じて判断する。見出し・箇条書き・表は情報が求める場合にだけ使い、短い修正には平文で十分である。

## 文体の基準

- 会話で口頭説明できる文章にする。ファイルパス、行番号、コードブロックは含めない。
- クラス名・メソッド名・変数名は、相手が同じコードベースで仕事をしている前提でそのまま使う。ただし場所の指定（ファイルパスや行番号）は付けない。
- 「〜を修正しました」のような作業報告で終わらせない。なぜその修正が必要だったのか（原因）と、なぜその修正方法を選んだのか（判断）を書く。
- 原因の説明は、何を見落としていたか・何を誤認していたかを具体的に述べる。「確認不足でした」のような抽象的な反省は書かない。
- 副作用がないことの根拠を、呼び出し元の構造から説明する。「問題ありません」だけで終わらせない。

## 判断基準

出力する返信コメントは、常に以下の論理構成をベースにする。

1. **誤認の背景**: 何をして、なぜそれで完了したと思い込んでいたか
2. **見落とし**: 実際にはどこで何が使われていたのを確認しそびれていたか
3. **本来の判断**: それを確認していれば、本来どういう実装判断になっていたか

**構成例（理想的な回答例）**:
> 「BadgeContainerView に4K対応を入れた時点で完了したと思い込んでいましたが、プレイヤーや一覧セルなどのフォールバック処理で FetchEventData 経由の createTagList がまだ使われているのを確認していれば、createTagList 側にも4K判定を残す判断になっていました。」

- 修正によって既存の動作が変わらないことを説明できる場合は、その根拠をこの構成の中に自然に組み込む。
- レビュー指摘の内容や見落としの背景が差分から推測できない場合は、自らコードを調査し、それでも不明な場合にのみユーザーに確認する。
