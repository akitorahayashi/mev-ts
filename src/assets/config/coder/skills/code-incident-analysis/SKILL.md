# コード上の障害調査

Issue、例外、コード位置、リポジトリを調査し、読者が最小の労力で原因、再現可否、必要な対応を判断できる報告を作る。ユーザーが指定した調査制約を守り、確認できない事実を仮定で補わない。

## 判定

1. ユーザー操作または処理の開始地点から失敗箇所まで、呼び出し、状態変更、非同期処理の開始と完了を順に辿る。
2. 正常時と失敗時が最初に分かれる地点を比較し、破られた値または状態の関係を原因として特定する。
3. クラッシュ経路の再現可否を次のいずれかに決める。
   - コード上で再現する: 具体的な入力、状態、実行順序によって失敗へ到達する。入力が本番で生まれた理由が不明でも、この判定は変わらない。
   - コード上で再現しない: 関連する経路ではコード上の検査によって失敗へ到達しない。
   - コード上では判定不能: 具体的な失敗状態を置いても、確認できない実行時挙動がなければ失敗への到達を判断できない。
4. 本番で失敗状態が生まれた理由と、通常のユーザー操作による再現可否は、クラッシュ経路とは別に判定する。
5. 原因を入力境界で防ぎ、正常時の動作を維持する一つの変更を根本対応とする。同じ不正な処理を持ち、同じ変更が必要な実装だけを影響範囲に含める。

## 説明

失敗へ至る最短の因果関係だけを、初めてコードを読む人にも分かる言葉で説明する。各主張の直後にコードリンクを置き、同じ事実を複数の節で説明しない。判定や根本対応を変えない場合分け、調査履歴、棄却した仮説、任意の改善案は含めない。

## 出力

調査対象リポジトリのルートに`./.tmp/code-incident-analysis/`を作成し、[出力テンプレート](assets/template.md)を使ったMarkdown文書を1調査につき1ファイル保存する。ファイル名は調査対象と問題を表すケバブケースとし、例として`meta-ec-banner-section-mismatch.md`の形式を取る。同じ調査のファイルが存在する場合は、そのファイルを正本として更新し、別名の重複を作らない。

構成、説明の詳しさ、根拠の置き方は[ECバナーのsection不整合の出力例](examples/meta-ec-banner-section-mismatch.md)を基準とし、事例固有の原因、値、修正は他の調査へ流用しない。チャットには作成または更新したファイルへのリンクだけを返し、報告本文を重複して出力しない。コード変更は、ユーザーが依頼した場合だけ行う。
