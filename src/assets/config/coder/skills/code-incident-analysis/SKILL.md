# コード上の障害調査

成果物は、調査過程を読まなくても、読者がエディタ上で原因までの経路を確認し、必要な対応を判断できる調査報告とする。

## 入力

ユーザーから提示されたIssue本文、例外またはスタックトレース、コード位置、リポジトリ、調査上の制約などを根拠として扱う。結論を出す前に、足りないコード上の文脈をリポジトリ内で調査する。

根拠は次の3段階に分ける。

- 観測済み: Issue、例外、トレース、ログなど、提示された記録から確認できる事実
- コード上で確定: リポジトリ内の具体的な入力、状態、実行順序から到達可能と証明できる事実
- 未確定: 入手できない本番データ、実行時挙動、外部記録に依存する事実

不足する根拠を仮定で補わない。不足している事実は、再現可否または根本対応の判定を妨げる場合だけ明示する。

## 調査範囲

このスキルの責務は調査と報告である。コード変更は、ユーザーが実装も依頼した場合だけ行う。

ビルド、テスト、端末、ネットワーク、外部システムに関するユーザーの制約を守る。静的調査の結果を実行確認済みとは扱わない。

## 分析方法

1. 観測された例外、失敗したシンボル、具体的な値を特定する。
2. 失敗する処理から呼び出し元へ遡り、ユーザー操作またはシステム上の開始地点から失敗箇所までを順方向にも辿る。
3. 失敗に影響する状態変更を記録する。非同期処理では、それぞれの開始、完了、結果を左右する完了順序を特定する。
4. 正常経路と異常経路を比較し、最初に状態が分かれる地点を特定する。
5. 値または状態の具体的な関係として、破られた不変条件を特定する。
6. 判定は次のいずれかとする。
   - コード上で再現する: 指定された入力と実行順序によって、リポジトリ内に失敗まで到達する経路がある。
   - コード上で再現しない: リポジトリが所有する検証によって、すべての関連経路で不変条件が守られる。
   - コード上では判定不能: 必要な状態遷移が、確認できない実行時挙動または外部システムに依存する。
7. 再現する場合は、必要な状態を作って失敗箇所へ到達する因果関係を再現手順に変換する。判定不能の場合は、代わりに不足している根拠を具体的に示す。
8. 破られた不変条件から根本対応を導き、正常動作が最後まで継続することを確認する。
9. 同等実装を検索し、同じ不変条件に従うすべての呼び出し箇所を影響範囲の判定に含める。

## 根本対応の判定基準

根本対応は、すべての関連する入力と実行順序で不変条件を保証し、意図された正常動作を維持し、同じ契約を持つ同等実装を対象に含む。

判定は一つに絞る。提案済みの修正で十分な場合は、異常状態を防げる理由と正常経路が継続する理由を示す。不十分な場合は、必要な代替修正と、提案済みの修正後にも残る失敗経路を示す。

必要な対応だけを含める。キャンセル、リファクタリング、防御的チェック、整理は、不変条件の保証または正常動作の維持に必要な場合だけ含める。

## 初心者が検証できる説明

読者は、ファイルを開いてメソッド呼び出しを追える一方、リポジトリ構造やフレームワーク内部を知らないものとする。

- 技術的な値は、それが何を表すかと同時に導入する。
- インデックスや件数は、曖昧さを防ぐ必要がある場合に人間が理解できる意味へ置き換える。
- 「データ」「処理」などの抽象語を避け、対象のリクエスト、状態、シンボル、コールバックを明記する。
- 因果関係の各段階にはソースコードへのリンクを置き、開始地点、変化する状態、次に実行される処理を示す。
- コードリンクは、開始地点から失敗箇所までエディタ上で上から順に辿れる並びにする。
- `発生順序`にはコード上の実行順序を、`再現手順`にはその状態を作る人間の操作を置く。
- 根拠は、それが支える主張の直後に置く。独立した根拠コード一覧は作らない。
- 同じ値の比較には表を、実行順序には番号付きリストを使う。
- 検索コマンド、調査ログ、棄却した仮説、無関係な実装説明、判断していない改善案は含めない。

読者が、最初に何が実行され、どの値が不正になり、どのコードがその値を使い、なぜ失敗し、なぜ提案する修正で防げるかを答えられる状態を完了とする。

## 出力

調査報告は、[出力テンプレート](assets/template.md)を使用してチャット上に返す。見出し構造は維持し、ユーザーが日本語以外で会話している場合だけ見出しを翻訳する。ユーザーが依頼しない限り、永続的な報告ファイルは作成しない。
